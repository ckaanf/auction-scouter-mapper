# 경매장 찜 목록에서 환산기까지: 반복 입력을 줄이기 위해 만든 크롬 확장 프로그램 회고

> 메이플스토리 웹 경매장의 장비 후보를 환산 주스탯 아이템메이커로 옮기는 반복 작업을 줄이기 위해, 브라우저 안에서 두 서비스를 연결하는 확장 프로그램을 만들었다.

## 출발점: 반복 작업을 줄이고 싶었다

장비를 비교할 때 경매장에서 후보를 찾고 찜해 둔 뒤, 환산기에서 다시 같은 옵션을 입력하는 흐름이 반복됐다. 후보가 늘어날수록 단순 입력은 실수하기 쉬운 일이 됐고, 여러 캐릭터를 관리하면 이전에 비교했던 세트를 다시 찾는 일도 많아졌다.

처음 목표는 작았다. 경매장 찜 목록의 장비 데이터를 읽어 환산기 아이템메이커에 옮기자. 다만 실제로 쓰기 시작하면 다음 작업도 자연스럽게 이어질 것 같았다. 이전 세트를 보관하고, 현재 장비를 불러오고, 다음 스펙업 후보를 내 기준으로 정리하는 일들이다.

## 해결 전략: 브라우저 안에서 두 서비스를 연결하기

별도 서버를 두기보다 Chrome 확장 프로그램으로 만들었다. 사용자가 이미 경매장과 환산기를 브라우저에서 사용하고 있으므로, 그 흐름을 끊지 않는 편이 맞다고 생각했다.

경매장 페이지에서는 찜 목록 응답을 받아 확장 프로그램 저장소에 동기화한다. 이때 현금 아이템과 환산 계산 대상이 아닌 슬롯은 제외하고, 찜 해제나 판매 종료 상태도 함께 관리한다. 팝업에서는 사용자가 비교할 장비만 선택해 환산기 쪽으로 보낼 수 있다.

환산기 쪽에서는 아이템메이커가 사용하는 장비 보관 데이터 형식에 맞춰 장비를 변환한다. 새 탭을 열고 페이지 문맥에서 보관 목록을 갱신한 뒤 새로고침하는 방식으로, 사용자는 결과를 환산기 화면에서 바로 확인할 수 있다.

## 가장 신경 쓴 지점: 데이터 변환과 안전한 주입

이 프로젝트에서 핵심은 버튼이나 화면보다 데이터 경계였다. 경매장 장비 데이터는 그대로 환산기에 넣을 수 없기 때문에, 슬롯·직업군·옵션·잠재능력·스타포스처럼 환산에 필요한 값을 아이템메이커 스키마로 정리해야 했다.

특히 직업군마다 의미 있는 주스탯이 다르다는 점을 반영했다. 변환 단계에서 직업군별 유효 스탯을 구분하고, 장비 옵션을 일정한 순서의 구조로 만들었다. 결과가 쉽게 깨지는 영역이라 매퍼와 백그라운드 메시지 흐름에 Jest 테스트를 붙였다.

주입은 더 조심해야 했다. 목록에 장비를 추가하는 흐름과, 저장한 세트로 기존 목록을 교체하는 흐름은 위험도가 다르다. 그래서 교체 작업에는 대상 폴더와 장비 수를 확인하는 창을 두고, 사용자 가이드에도 덮어쓰기 가능성을 명시하기로 했다. 자동화가 편리해질수록 되돌릴 수 있는 지점과 확인 문구가 중요하다는 걸 다시 배웠다.

## 기능을 확장하며 배운 것

단방향 내보내기만으로도 목적은 어느 정도 달성했지만, 사용하다 보면 장비 세트를 남기고 싶었다. 그래서 환산기에서 현재 장비나 아이템메이커 보관 목록을 가져와 확장 프로그램의 폴더에 저장하는 보관함 기능을 추가했다. 본캐, 부캐, 특정 장비 비교처럼 사용자의 맥락으로 세트를 나눌 수 있게 된 것이다.

다음으로는 환산기에서 보는 스펙업 순서에 내 조건을 반영하고 싶었다. 목표 최종뎀, 교환불가 가중치, 조각 가격, 환불 가격을 입력받아 비용과 상승량을 정리하고, 기준선에 해당하는 항목을 환산기 화면에서도 눈에 띄게 표시하도록 했다.

이 과정에서 기능이 늘어날수록 “어떤 값을 사용자가 결정하고, 어떤 값은 원본 서비스가 제공하는가”를 명확히 해야 했다. 확장 프로그램은 판단을 대신하기보다, 사용자가 정한 조건으로 비교를 더 빠르게 할 수 있도록 돕는 쪽에 머물러야 했다.

## 테스트와 사용자 확인 흐름

외부 사이트와 연동하는 확장 프로그램은 화면 구조나 데이터 형식이 바뀌면 쉽게 영향을 받는다. 모든 상황을 완벽히 막을 수는 없지만, 적어도 내 코드가 변환한 데이터와 메시지 흐름은 검증 가능해야 했다. 그래서 매퍼, 백그라운드 동작, 대표 데이터의 스냅샷을 Jest로 확인하는 기반을 만들었다.

사용자 경험에서는 단계별 확인도 중요했다. 찜 목록이 비어 있을 때는 먼저 경매장 찜 목록 페이지를 방문해야 한다는 안내가 필요했고, 교체처럼 돌이키기 어려운 작업에는 명시적인 확인이 필요했다. 구현과 문서가 따로 놀지 않도록 사용자 가이드를 저장소 안의 Markdown 원본으로 관리하기로 한 이유도 여기에 있다.

## 한계와 다음 개선점

이 확장 프로그램은 메이플스토리 웹 경매장과 MapleScouter의 현재 UI·데이터 형식에 의존한다. 외부 서비스가 바뀌면 수집·주입·강조 표시 중 일부가 동작하지 않을 수 있다. 또한 데이터는 브라우저 로컬 저장소를 중심으로 관리하므로, 기기나 브라우저 프로필을 넘는 동기화는 제공하지 않는다.

다음 개선에서는 실제 사용 흐름에서 자주 막히는 지점을 더 쉽게 진단하는 안내, 사이트 변경을 빠르게 감지할 수 있는 검증, 그리고 스크린샷을 포함한 사용자 문서의 지속적인 업데이트를 우선하고 싶다. 기능을 더하는 것만큼, 이미 만든 흐름을 오래 이해할 수 있게 유지하는 일이 중요하다고 느꼈다.

## 마치며

이 프로젝트는 거대한 플랫폼을 만들기보다, 내가 반복해서 겪던 작은 마찰을 줄이려는 시도에서 시작했다. 그 과정에서 데이터 변환, 외부 웹앱 연동, 확인 가능한 자동화, 문서화가 하나의 제품 경험으로 이어진다는 점을 배웠다.

본 글에서 소개한 확장 프로그램은 넥슨 및 MapleScouter와 무관한 개인 프로젝트다. 외부 서비스의 변화와 데이터 관리에 따른 사용 결과는 사용자가 확인해야 한다.
