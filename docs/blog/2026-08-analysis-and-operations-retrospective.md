# 개발 회고 2: 단순 연동을 넘어 분석기로 — 외부 데이터 역공학과 크롬 익스텐션 운영 설계

> 경매장 데이터를 환산기로 옮기는 브릿지를 만든 뒤, “그래서 지금 무엇을 강화하는 편이 좋은가?”라는 다음 질문에 답하기 위해 분석 정확도와 운영 안전장치를 함께 설계한 기록이다.

## 다음 단계의 고민: 데이터를 옮긴 다음은?

1차 배포에서 경매장 찜 목록 장비를 환산기 아이템메이커로 옮기는 흐름을 만들었다. 이후 폴더 기반 보관함을 추가하면서 캐릭터별 장비 세트도 관리할 수 있게 됐다.

직접 사용하다 보니 다음 문제가 남았다. 후보 장비를 환산기에 올릴 수는 있지만, 내 재화 가치와 목표를 기준으로 어떤 선택이 더 효율적인지는 여전히 따로 판단해야 했다. 환산기에는 스펙업 효율 데이터가 있었지만, 교환불가 재화에 부여하는 가치나 환불·조각 가격은 사용자마다 다르다.

그래서 확장 프로그램 안에서 목표 최종뎀, 교환불가 가중치, 조각 가격, 환불 가격을 받아 **100억 메소당 최종뎀 상승량** 기준으로 항목을 정리하는 분석 기능을 추가했다. 목표는 정답을 대신 고르는 것이 아니라, 사용자가 세운 가격 기준으로 비교 과정을 줄이는 것이었다.

## 블랙박스를 열어라: 외부 데이터 역공학

가장 어려웠던 지점은 원본 사이트가 내려주는 효율값과 확장 프로그램의 정렬 결과가 완전히 일치하지 않았다는 점이다. 특히 추가옵션 비용을 사용자의 환불 시세로 바꾸는 순간 순서가 어긋났다.

처음에는 특정 장비군의 숨은 프리미엄이나 별도 가중치를 의심했다. 추측을 계속 늘리는 대신, API 배열의 기대 비용과 효율값을 표로 비교하고 다음 관계를 역산했다.

```text
원본 기대 비용 = 기준 환불 가격 × 예상 시행 횟수
예상 시행 횟수 = 원본 기대 비용 ÷ 0.025억
사용자 기준 비용 = 예상 시행 횟수 × 사용자 환불 가격 × 교환불가 가중치(해당 시)
효율 = 최종뎀 상승량 ÷ 사용자 기준 비용
```

이 과정에서 원본 데이터가 환불 1개당 `0.025억`이라는 고정 기준으로 기대 비용과 효율을 계산한다는 점을 확인했다. 중요한 것은 숫자 하나를 맞히는 일이 아니라, 원본의 기준값과 사용자의 가격 기준을 분리해 다루는 구조를 찾은 일이었다.

예외도 같이 다뤘다. 일반 강화·잠재·작·추가옵션 데이터는 교환가능/교환불가 배열이 나뉘어 있고, 사용자가 정한 교환불가 가중치는 교환불가 항목에만 적용된다. 추가옵션은 원본 기대값을 곧바로 가격으로 쓰지 않고 먼저 시행 횟수로 환산해야 했다. 초기 가설과 다른 데이터가 나오면 가설을 버리고 입력값·예외 배열·계산 단위를 다시 확인하는 과정을 반복했다.

이 경험은 외부 시스템을 연동할 때 “화면에 보이는 정렬”만 복제하는 것보다, 그 결과를 만드는 단위와 기준값을 검증하는 일이 먼저라는 점을 보여 줬다.

## 크롬 웹스토어라는 야생: 업데이트보다 빠른 통제

정확도를 높이는 것과 별개로 운영 위험도 커졌다. 확장 프로그램은 메이플스토리 웹 경매장과 환산기라는 외부 사이트의 UI·데이터 형식에 의존한다. 사이트가 바뀌어 기능이 깨져도 스토어 심사를 거친 새 버전이 사용자에게 도달하기까지 시간차가 생길 수 있다.

이 간격을 줄이기 위해 별도 서버 대신 GitHub Gist의 JSON을 원격 설정으로 사용했다. 백그라운드 서비스 워커는 설치 시와 60분 주기마다 원격 설정을 가져와 `chrome.storage.local`에 저장한다. 팝업은 저장된 설정을 읽어 다음 행동을 할 수 있다.

- 최소 요구 버전보다 낮은 확장 프로그램에는 업데이트 안내를 표시한다.
- 경매장 찜 목록·보관함 또는 스펙업 분석 기능을 각각 비활성화한다.
- 문제가 발생했을 때 기능 탭 상단에 공지 배너를 표시한다.

핵심은 원격 설정이 기능을 고쳐 주는 만능 장치가 아니라는 점이다. 잘못된 동작을 사용자에게 계속 노출하지 않고, 업데이트 전까지 위험한 흐름을 멈추고 상황을 설명하는 **운영 안전장치**다.

## 기능 구현에서 운영 가능한 제품으로

1차 개발에서는 데이터를 읽고 변환하고 주입하는 흐름을 만들었다. 이번 단계에서는 그 흐름의 결과가 왜 그렇게 나오는지 검증하고, 외부 환경 변화가 생겼을 때 사용자를 어떻게 보호할지 고민했다.

- 계산식은 원본 데이터·예외 배열·단위를 비교해 검증한다.
- 사용자 가격 기준은 원본 기준값과 분리해 명시적으로 적용한다.
- 위험한 기능은 업데이트 배포와 별개로 비활성화·공지할 수 있게 한다.
- 분석 결과와 설정은 로컬에 남겨 사용자가 다시 확인할 수 있게 한다.

작은 사이드 프로젝트이지만, 기능이 돌아가는 것과 사용자가 안전하게 계속 쓸 수 있는 것은 다른 문제라는 걸 배웠다.

## 다음 개선점

외부 의존성이 있는 만큼, 앞으로도 실제 사용 흐름을 기준으로 점검해야 한다. 사이트 변경을 더 빨리 감지하는 검증, 설정 갱신 실패 시의 사용자 안내, 실제 화면을 담은 사용자 가이드 보완이 다음 과제다.

회고도 같은 방식으로 관리하려 한다. 모든 수정에 장문 글을 쓰기보다, 릴리스 노트에는 사실과 변경점을 짧게 남기고, 이번처럼 문제 정의와 설계 방식이 바뀌는 전환점에서는 별도의 회고로 맥락을 정리한다.

## 마치며

이 프로젝트는 단순한 데이터 운반 도구에서 시작했지만, 지금은 사용자의 비교와 판단을 돕는 분석 도구를 지향한다. 블랙박스 데이터를 역산해 기준을 확인하고, 통제하기 어려운 외부 환경에는 원격 설정으로 방어막을 두는 과정에서 구현과 운영이 분리될 수 없다는 것을 배웠다.

본 프로젝트는 넥슨 및 MapleScouter와 무관한 개인 프로젝트다. 분석 결과는 사용자의 입력값을 바탕으로 한 참고 정보이며, 실제 게임 결과나 비용을 보장하지 않는다.
